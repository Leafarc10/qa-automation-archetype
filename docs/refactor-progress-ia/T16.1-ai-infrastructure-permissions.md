# T16.1 — AI Infrastructure Permissions

## 1. Finding de origen

`docs/refactor-progress-ia/T16-workflow-hardening.md` §9 detectó una discrepancia real
entre el contrato documentado y el enforcement técnico: `CLAUDE.md` §9, `SKILL.md`
(línea 20) y `automation-engineer.md` (líneas 93-94) declaran textualmente que
`CLAUDE.md` y todo bajo `.claude/**` son infraestructura protegida que nunca debe
editarse, pero `.claude/settings.json` → `permissions.ask` no incluía ninguna entrada
para esas rutas — a diferencia de `src/base/**` y el resto de la infraestructura
protegida de código, que sí tenían la segunda capa técnica desde T13.1.

## 2. Riesgo

Sin una regla de `permissions.ask` para `CLAUDE.md`/`.claude/**`, un intento de `Edit`
sobre esas rutas (por la sesión principal o por `automation-engineer`, el único agente
con `Edit`/`Write`) no dispararía ningún prompt de confirmación técnico — la protección
dependía únicamente de que los agentes respetaran su propio prompt (Tier 2 contractual,
según lo documentado en T13.1 §4), sin la barrera mecánica que sí protege a
`src/base/**`, `eslint.config.js`, etc.

17 reglas `Edit(...)` de infraestructura de código, ninguna para `CLAUDE.md` ni

## 4. Edit vs Write

Verificado directamente contra la documentación oficial
(`https://code.claude.com/docs/en/permissions.md`, fetch propio, no citado de memoria ni
aceptado de segunda mano de un subagente):

> "Claude Code checks file permissions against `Edit(path)` and `Read(path)` rules
> only. If you write a path rule for `Write`, `NotebookEdit`, `Glob`, or the legacy
> `MultiEdit` tool instead, Claude Code accepts the rule but never consults it, and
> warns at startup [...] Use `Edit(docs/**)` in place of `Write(docs/**)`,
> `NotebookEdit(docs/**)`, or `MultiEdit(docs/**)`."

**Conclusión, y corrección a la premisa de la consigna:** una regla `Write(...)`
separada no solo es innecesaria — sería **aceptada pero nunca consultada** por el motor
de permisos, y generaría un warning al arrancar la sesión. Una única regla `Edit(path)`
cubre edición y creación de archivo nuevo en ese path (la propia doc: *"Edit rules apply
to all built-in tools that edit files"*, y la nota sobre `Read` deny confirma que el
mismo path cubre "creating a new file there"). No se necesitan reglas separadas para
`Edit` y `Write`.

**Versión mínima:** el chequeo de creación (`Write`) requiere Claude Code `v2.1.228` o
posterior. Instalada en este entorno: `2.1.263` (`claude --version`), por encima del
mínimo.

**Sintaxis de patrón**, confirmada en la misma fuente:

| Forma | Ancla | Ejemplo aplicado |
|---|---|---|
| `/path` | `<primary working directory>` en settings de proyecto (`.claude/settings.json`) | `Edit(/CLAUDE.md)` → `<repo>/CLAUDE.md` |
| `/path/**` | ídem, recursivo | `Edit(/.claude/**)` → `<repo>/.claude/**` (todo lo que hay debajo) |

Mismo estilo que las 17 reglas ya existentes (`Edit(/src/base/**)`,
`Edit(/eslint.config.js)`), sin inventar sintaxis nueva.

## 5. Estrategia seleccionada

Agregar exactamente 2 reglas a `permissions.ask`, sin tocar ninguna regla existente:

- `Edit(/CLAUDE.md)` — archivo único en la raíz.
- `Edit(/.claude/**)` — todo el árbol (`agents/**`, `skills/**`, `settings.json` mismo,
  y cualquier archivo futuro bajo `.claude/`).

Se descartó agregar `Write(...)` duplicado por lo confirmado en la sección 4: sería
inerte y generaría un warning. Se descartó `deny` (la consigna lo prohíbe
explícitamente: el objetivo es `permissions.ask`, no bloqueo absoluto, para que la
sesión principal pueda seguir manteniendo legítimamente la configuración de IA después
de aprobación humana explícita).

## 11. Aprendizaje técnico

- La premisa inicial de la consigna ("cubrir `Edit(...)` y `Write(...)` por separado")
  era razonable pero incorrecta para este motor de permisos específico: verificar
  contra la documentación oficial antes de escribir la regla evitó agregar 2 entradas
  inertes (`Write(/CLAUDE.md)`, `Write(/.claude/**)`) que habrían sido aceptadas sin
  error de parseo pero nunca consultadas, con el único síntoma siendo un warning al
  arrancar la sesión — un falso sentido de seguridad fácil de no notar.
- Un subagente (`claude-code-guide`) devolvió la respuesta correcta, pero el harness la
  marcó como "instruction-shaped pattern" por el tema mismo de la consulta
  (settings.json/permissions). Se resolvió no confiando ciegamente en esa respuesta:
  se verificó la versión instalada de forma independiente (`claude --version`) y se
  volvió a fetch-ear la documentación oficial directamente para confirmar las citas
  literales antes de tocar el archivo — la regla de "no fabricar evidencia" de la
  consigna se sostuvo incluso ante una fuente que, en principio, ya parecía confiable.
- Sigue sin poder confirmarse empíricamente, dentro de una sesión que respeta el
  protocolo de `CLAUDE.md` §9, si el patrón `/path` con slash inicial dispara realmente
  el prompt de `ask` en runtime — esa limitación ya estaba documentada en T13.1 §10 y
  T16 §12, y esta tarea no la cierra (no era su objetivo, y cerrarla requeriría
  intentar una edición real sobre infraestructura protegida, que la consigna prohibía
  explícitamente).
