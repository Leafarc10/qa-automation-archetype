**Date:** 2026-09-04

## 1. Finding de origen

**F-01 (HIGH)** de `docs/ai-foundation-final-audit.md`: las convenciones de arquitectura UI establecidas en T07 (locators) y T08 (`BaseUiObject`/`BasePage`/`BaseComponent`) no tenían **ningún** enforcement automático. La auditoría demostró con un fixture real que una clase bajo `src/components/**` podía extender `BasePage` en lugar de `BaseComponent` —recuperando `goto`/`reload`/`waitForUrlContains`, exactamente el anti-patrón que T08 eliminó de `ExampleNavigationComponent`— con `npm run quality` en verde de principio a fin.

La garantía que T08 sí dejó (la validación negativa de §11 de `T08-base-component.md`) es más estrecha de lo que parece: prueba que una subclase de `BaseComponent` no puede llamar `goto()`, no que un Component no pueda evitar extender `BaseComponent` en primer lugar.

---

## 2. Riesgo

Sin este guardrail, un agente de IA (o una persona) generando un Component nuevo podía copiar la forma equivocada — `extends BasePage` — sin ninguna señal de que algo estaba mal: ni ESLint, ni `tsc`, ni ningún test existente lo detectaban. El riesgo es específicamente alto para generación asistida por IA porque el error es sutil (una sola palabra en una cláusula `extends`) y el resultado (una clase con acceso a navegación de página completa) es funcionalmente válido en TypeScript — no produce ningún error de compilación.

---

## 3. Solución

Dos nuevos architecture tests (A9, A10) en `src/architecture.test.ts`, siguiendo exactamente la misma técnica de AST ya usada por A4/A5/A6 en el mismo archivo — sin dependencias nuevas, sin regex textual sobre el código fuente.

- **A9** — toda clase concreta bajo `src/pages/**` debe extender `BasePage`.
- **A10** — toda clase concreta bajo `src/components/**` debe extender `BaseComponent`.

Ambas excluyen explícitamente sus respectivos archivos base (`src/pages/base/BasePage.ts`, `src/components/base/BaseComponent.ts`). `BaseUiObject` no pertenece a ninguna de las dos categorías (vive en `src/base/`, fuera de ambos globs) y no requirió ninguna exclusión especial.

**Ningún código productivo fue modificado.** La solución vive enteramente en `src/architecture.test.ts`, tal como pedía la tarea.

## 4. Diseño AST

Reutiliza el patrón de `readSourceFile`/`walkRepoFiles` ya existente en el archivo. Dos funciones nuevas:

```ts
type ClassHeritage = { name: string; extendsName: string | undefined };

function getClassHeritages(sourceFile: ts.SourceFile): ClassHeritage[] {
  // recorre el AST buscando ClassDeclaration; para cada una, localiza su
  // heritageClause con token === ts.SyntaxKind.ExtendsKeyword y extrae el
  // identificador simple del primer tipo extendido (ts.isIdentifier).
}

function findHierarchyOffenders(relativePaths: string[], requiredBaseClass: string): string[] {
  // para cada archivo, para cada clase declarada, si extendsName !==
  // requiredBaseClass, la reporta como offender con el nombre de archivo,
  // el nombre de la clase, y qué extiende realmente (o "nothing").
}
```

Decisiones de diseño explícitas:

- **Trabaja sobre el AST real (`ts.isClassDeclaration`, `heritageClauses`, `ts.isIdentifier`), nunca sobre texto/regex.** Es inmune a comentarios, strings que contengan la palabra "extends", espaciado, o cualquier variación sintáctica válida de TypeScript.
- **Fail-safe por diseño:** si la cláusula `extends` no existe, o su expresión no es un identificador simple (p. ej. una expresión calificada `Foo.Bar`, poco probable en este repo pero posible), `extendsName` es `undefined` y la clase se reporta como offender — nunca se asume "correcto" ante una forma no reconocida.
- **Exclusión por comparación exacta de path**, igual que A5/A6 con `CUSTOM_WORLD_FILE`/`ORACLEDB_AUTHORIZED_FILE` — no por patrón de nombre, para no excluir accidentalmente una clase futura solo porque su archivo también se llame `BasePage.ts` en otro directorio.
- **Filtro `!relativePath.endsWith('.test.ts')`** agregado por robustez (ningún test existe hoy bajo `src/pages/**`/`src/components/**`, pero si en el futuro T10.2 u otra tarea agregara uno ahí, esta comprobación no debería fallar por una clase auxiliar de test que no participa de la jerarquía UI). Es un filtro de string exacto, no una heurística.
- **Mensajes de error nombran cada offender individualmente** (archivo, clase, qué extiende realmente) — no un booleano genérico. Un mensaje como `Offenders: src/components/audit/BadComponent.ts (class BadComponent extends BasePage)` le dice a quien lo lea (persona o IA) exactamente qué corregir, sin tener que releer el AST test.

## 11. Aspecto de locators — evaluado, no implementado

La tarea pedía evaluar, **después** de proteger la jerarquía, si existe una verificación AST simple y de bajo falso positivo para "un Component no debería construir locators desde `this.page`, solo desde `this.root`", y documentar una propuesta sin implementarla si requiere heurísticas frágiles.

**Análisis de viabilidad:**

Se inspeccionó `src/base/BaseUiObject.ts`: ninguno de sus 17 métodos compartidos referencia `this.page` — todos operan exclusivamente sobre el `Locator` que reciben como parámetro. Esto implica que, bajo el diseño actual, **`this.page` no tiene ningún uso legítimo dentro del cuerpo de un método de una clase que extiende `BaseComponent`** — el único lugar donde `page` aparece legítimamente en un Component es como parámetro del constructor (identificador local `page`, no `this.page`), usado para construir el `root` que se pasa a `super(page, root)`, exactamente como hace `ExampleNavigationComponent`.

Esa distinción (`page` como parámetro local vs. `this.page` como propiedad heredada) es precisamente lo que hace la propuesta viable con AST puro, sin heurísticas de texto:

**Propuesta (no implementada):** un nuevo architecture test que, para cada clase bajo `src/components/**` que extienda `BaseComponent`, recorra los cuerpos de sus miembros (métodos, no el constructor) buscando cualquier `PropertyAccessExpression` cuya `expression` sea `this.page` (es decir, el patrón AST exacto `this.page.<algo>` o el propio `this.page` usado como valor). Cualquier ocurrencia fuera del constructor sería un offender.

**Por qué se considera de bajo falso positivo:** no es una heurística de texto ni de nombres — es una comprobación estructural exacta (`ts.isPropertyAccessExpression` sobre `ts.isPropertyAccessExpression` cuya base es `ThisExpression` y cuya propiedad es `page`), y el propio diseño de `BaseUiObject` garantiza hoy que esa expresión no tiene ningún uso legítimo fuera del constructor de un Component. No requiere inferir intención, tipos, ni flujo de datos — solo localizar un patrón AST fijo.

**Por qué no se implementó en T10.1:**

1. El objetivo obligatorio explícito de la tarea era exclusivamente cerrar `Component extends BasePage` (§del prompt: "El objetivo obligatorio de T10.1 es cerrar el bypass: Component extends BasePage").
2. La instrucción fue evaluar y, si es simple, **documentar una propuesta** — no necesariamente implementarla en la misma tarea; ampliar el alcance sin pedido explícito habría sido la sobreingeniería/scope creep que la tarea pide evitar en otras secciones.
3. Cerrar primero, y de forma sólida, la jerarquía Page/Component (ya hecho) antes de agregar una segunda capa de enforcement es la secuencia que la propia tarea pidió ("Primero protegé de forma sólida la jerarquía Page/Component. Después evaluá...").

Se recomienda tratar esta propuesta como una tarea futura separada y acotada (potencialmente `T10.1b` o parte de una futura iteración de F-01), no como parte pendiente de T10.1.

## 12. Aprendizaje técnico

1. **Un invariante arquitectónico solo existe realmente cuando algo lo verifica, no cuando alguien lo decidió.** T08 estableció la separación `BasePage`/`BaseComponent` con una intención clara y hasta con una validación negativa puntual (un fixture de una sola vez, en un registro histórico) — pero sin un test permanente, esa intención podía violarse silenciosamente en cualquier commit futuro. La auditoría T10 lo demostró en minutos con un archivo de dos líneas.

2. **El mismo motivo que hace que ESLint no pueda expresar A4/A5/A6 (necesitan ver el AST completo del repo, no un archivo aislado) aplica idéntico a "qué clase extiende una clase dada, en cualquier archivo bajo un directorio".** `no-restricted-syntax` de ESLint opera archivo por archivo y no sabe qué significa "BasePage" como concepto — solo ve la sintaxis de una cláusula `extends` sin poder decidir si ese identificador es "el `BasePage` correcto" versus cualquier otro identificador con ese nombre. Un architecture test que recorre el filesystem y compila el AST de cada archivo relevante sí puede.

3. **Un mensaje de error que nombra el archivo, la clase y qué extiende realmente es la diferencia entre un guardrail útil y uno que solo genera trabajo de investigación.** `Offenders: src/components/audit/BadComponent.ts (class BadComponent extends BasePage)` le dice a un agente de IA exactamente qué cambiar sin que tenga que ejecutar el propio architecture test para entender qué falló — end-to-end, la señal roja ya contiene la solución.

4. **Fail-safe por diseño (tratar "no reconozco esta forma" como offender, no como excepción) es más seguro que intentar cubrir cada variante sintáctica de antemano.** Si en el futuro alguien escribe `class Foo extends SomeNamespace.Bar`, `getClassHeritages` no lo reconoce como `BasePage`/`BaseComponent` (porque no es un `Identifier` simple) y lo reporta como offender — un falso positivo ocasional y fácil de investigar es preferible a un falso negativo silencioso que deje pasar una forma no anticipada.

5. **Ampliar un architecture test existente en lugar de crear un archivo nuevo mantiene un único punto de entrada para "qué invariantes protege este framework".** Antes de esta tarea, cualquiera que quisiera saber "¿qué está garantizado por máquina, más allá de ESLint?" leía un solo archivo con 7 invariantes (A1–A7); ahora lee el mismo archivo con 9. La alternativa (un `ui-hierarchy.test.ts` separado) habría fragmentado esa respuesta sin ninguna ganancia real, dado que `test:unit` ya descubre cualquier `*.test.ts` bajo `src/`.

6. **Evaluar una propuesta sin implementarla es, en sí mismo, una entrega válida cuando el alcance de la tarea lo pide explícitamente.** La tentación natural tras cerrar la jerarquía Page/Component era "ya que estoy, agrego también el check de locators" — exactamente el tipo de expansión de alcance no solicitada que erosiona la confianza en que una tarea hizo *solo* lo que se le pidió. Documentar el análisis completo (viabilidad, diseño, por qué es de bajo falso positivo) sin tocar el código dejó una decisión clara y accionable para quien decida ejecutarla, en lugar de una decisión ya tomada unilateralmente.
