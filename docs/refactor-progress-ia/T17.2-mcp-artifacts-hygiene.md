## 3. Git ignore analysis

Verificado empíricamente con `git check-ignore -v`, no asumido:

- **`.claude/settings.local.json`**: `git check-ignore -v` apuntaba a
  `"C:\Users\CFOTech/.config/git/ignore":1:**/.claude/settings.local.json` — es decir,
  ignorado únicamente por el **gitignore global del usuario** (`core.excludesFile`
  default, `~/.config/git/ignore`), **no** por ninguna regla del `.gitignore` del
  repo. Confirmado además con `git config --get-all core.excludesfile` (vacío — usa el
  default de XDG) y leyendo ese archivo global directamente: su único contenido
  relevante es `**/.claude/settings.local.json`.
- **`.playwright-mcp/`**: la primera comprobación, hecha sobre un path que **todavía
  no existía en disco**, devolvió un resultado engañoso (`git check-ignore -v
  .playwright-mcp/` reportó una coincidencia falsa con `.gitignore:61`, línea que en
  realidad está en blanco — confirmado con `nl -ba .gitignore` y un dump hexadecimal).
  Repitiendo la prueba con un **archivo real** (`.playwright-mcp/test.yml`) y
  `git status --short`, quedó confirmado que el directorio **no estaba ignorado en
  absoluto**: aparecía como `??` (untracked). Este es exactamente el motivo por el que
  la consigna insistía en "no asumir" y usar `git check-ignore -v` con evidencia real,
  no solo sobre paths hipotéticos.

**Conclusión:** ninguno de los dos paths estaba protegido por una regla del **repo**;
uno dependía por completo de configuración personal de una máquina (no portable a un
clon nuevo), y el otro no estaba protegido en absoluto.

## 4. Prettier ignore analysis

Confirmado con `npx prettier --check <path>` directo sobre cada archivo (antes de
tocar nada):

- `.claude/settings.local.json` → Prettier lo inspecciona y lo marca con problemas de
  estilo (`format:check` falla).
- `.playwright-mcp/page-test.yml` (recreado para la prueba) → Prettier también lo
  inspecciona y lo marca (`.yml` no está excluido en `.prettierignore`).

Antes de decidir tocar `.prettierignore`, se probó empíricamente si **agregar ambos
paths solo al `.gitignore` del repo** ya alcanzaba para que Prettier los ignorase
(sin ninguna entrada nueva en `.prettierignore`). Resultado: **sí** —
`npx prettier --check` sobre ambos archivos, y luego `npm run format:check` completo,
reportaron `All matched files use Prettier code style!`. Esto confirma que Prettier
3.x (versión instalada en este repo, `^3.9.6`) respeta el `.gitignore` del repositorio
automáticamente además de `.prettierignore`, sin configuración adicional.

## 5. Solución seleccionada

**Agregar ambos paths únicamente a `.gitignore`. No tocar `.prettierignore`.**

| Path | ¿Va en `.gitignore`? | ¿Va en `.prettierignore`? |
|---|---|---|
| `.claude/settings.local.json` | **Sí** — es estado local de Claude Code (aprobación de MCP en esta máquina), nunca debe versionarse; depender del gitignore *global* del usuario no es portable a un colaborador nuevo o a CI, que es exactamente el problema para un arquetipo público/reutilizable | **No necesario** — confirmado empíricamente (§4) que Prettier ya deja de inspeccionarlo en cuanto está en `.gitignore` |
| `.playwright-mcp/` | **Sí** — mismo criterio que `test-results/`, `playwright-report/`, `blob-report/` (ya ignorados): artefacto generado por una herramienta, no código ni documentación | **No necesario**, mismo motivo |

No se agregó ningún script de limpieza (`rm -rf` en `pretest`/`posttest`, hooks, etc.):
el `.gitignore` por sí solo resuelve el problema completo (git status limpio +
Prettier deja de inspeccionar), así que un script adicional sería sobreingeniería no
solicitada.

## 12. Aprendizaje técnico

- `git check-ignore -v` sobre un path que **no existe todavía** puede devolver un
  resultado engañoso en Git para Windows (reportó una línea de `.gitignore` que en
  realidad está en blanco, como si coincidiera con `.playwright-mcp/`). La única forma
  confiable de verificar una regla de ignore es probarla contra un **archivo real** en
  disco y confirmar con `git status --short` — exactamente la disciplina que esta
  tarea pedía explícitamente ("no asumir").
- Prettier 3.x respeta el `.gitignore` del repositorio automáticamente, además de
  `.prettierignore` — no hace falta duplicar cada entrada de higiene de git en ambos
  archivos. Antes de agregar una entrada a `.prettierignore` vale la pena probar
  primero si el `.gitignore` ya alcanza.
- Un archivo generado por la propia herramienta (Claude Code aprobando un MCP,
  Playwright MCP guardando un snapshot) que depende únicamente del gitignore
  *personal* del usuario no es una solución portable para un arquetipo pensado para
  ser clonado por otros — la regla tiene que vivir en el `.gitignore` del repo para
  funcionar igual en una máquina nueva, sin asumir configuración previa de quien lo
  clona.
- Cuando un hallazgo de higiene se resuelve con una sola línea de `.gitignore`, no
  hace falta ningún script de limpieza adicional — resolver con la herramienta más
  simple que alcanza evita sobreingeniería.
