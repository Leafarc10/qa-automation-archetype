**Date:** 2026-09-04
**Status:** ✅ COMPLETED

## 1. Finding de origen

**F-04 (HIGH)** de `docs/ai-foundation-final-audit.md`: `test:unit` ejecutaba únicamente `src/**/*.test.ts`. La auditoría T10 demostró que un archivo `support/x.test.ts` con `assert.equal(1, 2)` nunca se ejecutaba, y `npm run test:unit`/`npm run quality` seguían reportando "todo verde" — un test muerto en silencio. El agravante que la auditoría señaló explícitamente: el propio README indicaba colocar los tests junto al código que prueban, lo que para `support/**` o `features/**` producía exactamente ese resultado.

---

## 2. Riesgo

Un test que nunca se ejecuta es peor que no tener ningún test: da la falsa sensación de cobertura. Para generación asistida por IA el riesgo es mayor — un agente que escriba un test para un cambio en `support/` o `features/`, siguiendo la convención documentada de "poné el test junto al código", recibiría un `npm run quality` en verde sin que su test hubiera corrido ni una sola vez.

## 4. Estrategia elegida

### 4.1. Verificación empírica previa (obligatoria antes de implementar)

Se probó, con fixtures temporales de solo lectura para el resultado (no tocaban `package.json` todavía), si `node --test` en Node v24.13.1 acepta múltiples patrones glob como argumentos separados, sin dependencias nuevas:

```bash
node --test "src/**/*.test.ts" "support/**/*.test.ts" "features/**/*.test.ts"
```

Con un archivo de prueba temporal en `support/` y otro en `features/`, ambos se descubrieron y ejecutaron correctamente (62 = 60 + 2 sondas). **Confirmado: funciona sin dependencias nuevas.**

### 4.2. Alternativa considerada y descartada

Se evaluó también una forma más compacta con expansión de llaves en un único glob:

```bash
node --test "{src,support,features}/**/*.test.ts"
```

Esta forma **también funcionó** empíricamente (mismo resultado: 62 tests descubiertos). Se descartó en favor de los tres globs explícitos por ser la forma más explícita y menos dependiente de una característica de glob más específica (expansión de llaves) que el `**` simple ya usado en el repo desde T03 — cada root queda nombrado literalmente, reduciendo la superficie de sorpresa si el motor de glob de `node --test` cambiara de comportamiento en una versión futura. Es también, literalmente, la forma que la propia tarea describe como "resultado conceptual esperado".

### 4.3. Decisión: defensa en profundidad, dos capas independientes

1. **Test runner** — `test:unit` amplía su discovery a los tres roots reales.
2. **Architecture test (A12)** — nuevo invariante que falla si aparece un `*.test.ts` fuera de esos tres roots.

Ninguna capa reemplaza a la otra: el runner ejecuta lo legítimo; el architecture test evita que algo se coloque donde el runner nunca lo vería.

## 6. Architecture guardrail

Nuevo invariante **A12** en `src/architecture.test.ts`, agregado a continuación de A11 (T10.1b):

```ts
const UNIT_TEST_DISCOVERY_ROOTS = ['src/', 'support/', 'features/'];

describe('architecture — every unit test lives under a test:unit discovery root', () => {
  it('has no *.test.ts file outside src/**, support/**, or features/**', () => {
    const offenders = walkRepoFiles().filter(
      (relativePath) =>
        relativePath.endsWith('.test.ts') &&
        !UNIT_TEST_DISCOVERY_ROOTS.some((root) => relativePath.startsWith(root))
    );

    assert.deepEqual(
      offenders,
      [],
      `Unit test is outside the test:unit discovery roots and would never execute. ` +
        `test:unit only runs ${UNIT_TEST_DISCOVERY_ROOTS.map((root) => `${root}**/*.test.ts`).join(', ')}. ` +
        `Offenders: ${offenders.join(', ')}`
    );
  });
});
```

Reutiliza `walkRepoFiles()`, ya existente desde T06, que ya excluye correctamente `node_modules`, `.git`, `reports`, `test-results`, `playwright-report`, `blob-report`, `coverage`, `.cache`, `.vscode`, `.idea`, `docs/refactor-progress/` (histórico) y cualquier directorio `.tmp-*` — no fue necesario tocar esa lista de exclusión. Cero dependencias nuevas; es un filtro de string exacto (`endsWith`/`startsWith`) sobre la lista de archivos reales del repo, no una heurística.

**Mensaje de error** — coincide exactamente con el sugerido por la tarea, e incluye el/los offender(s):

```
Unit test is outside the test:unit discovery roots and would never execute.
test:unit only runs src/**/*.test.ts, support/**/*.test.ts, features/**/*.test.ts.
Offenders: scripts/__t10_2_dead.test.ts
```

## 13. Aprendizaje técnico

1. **Ampliar un glob de discovery sin protegerlo con un segundo mecanismo solo mueve el problema, no lo resuelve.** Si T10.2 hubiera cambiado únicamente `test:unit` (paso 5) sin agregar A12 (paso 6), un test colocado en un cuarto directorio no anticipado (`scripts/`, `tools/`, `e2e-helpers/`, lo que sea) habría reproducido exactamente el mismo silencio que F-04 documentó — solo que en un lugar distinto. El invariante real que hay que proteger no es "corré los tests de estos tres directorios", es "ningún test puede vivir fuera de donde se ejecuta", y eso requiere una comprobación independiente del propio comando que hace el discovery.

2. **Verificar empíricamente antes de implementar evita comprometerse con una suposición sobre el comportamiento de una herramienta.** La tarea pedía explícitamente confirmar que Node 24.13.1 acepta múltiples globs sin asumirlo — se probó con fixtures reales antes de tocar `package.json`, y se descubrió además que una segunda forma (expansión de llaves) también funciona, lo que permitió una decisión informada entre dos alternativas válidas en lugar de una sola opción sin comparar.

3. **Cuando dos soluciones funcionan igual de bien, preferir la más explícita reduce el costo de mantenimiento futuro, no el de hoy.** `"{src,support,features}/**/*.test.ts"` es más corto, pero depende de que el motor de glob de `node --test` siga soportando expansión de llaves — una característica más específica que el `**` simple ya probado en este repo desde T03. Tres globs literales, uno por root, son inmediatamente legibles sin tener que recordar qué sintaxis de glob soporta Node, y decir exactamente lo mismo que la sección README que los describe.

4. **Un architecture test puede fallar por una razón completamente distinta a la que motivó su escritura, y eso es correcto, no un bug.** Durante la validación decisiva, A12 falló no porque su propia lógica estuviera mal, sino porque el fixture 3 (`scripts/__t10_2_dead.test.ts`) es precisamente el caso que existe para detectar. Ver a un test fallar exactamente cuando su fixture de prueba negativo está presente, y pasar limpio en su ausencia, es la única evidencia aceptable de que un guardrail realmente hace lo que dice — no basta con que el código "se vea razonable".

5. **Un test que pasaría si se ejecutara (fixture 3, `assert.equal(1,1)`) es la prueba más contundente del problema de F-04 — más que un test que falla.** Un test fallido fuera de discovery al menos generaría sospecha si alguien notara que nunca aparece en el output. Un test que *pasaría* si corriera, colocado fuera de discovery, no genera ninguna señal en ningún lugar — ni un fallo visible, ni una ausencia sospechosa, porque nadie espera verlo listado. Ese es precisamente el escenario que hace a F-04 "HIGH" y no "MEDIUM": la ausencia de señal es total, en ambas direcciones.
