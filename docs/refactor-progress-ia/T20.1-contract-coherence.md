## 3. H-01

**Antes** — `CLAUDE.md` §8, párrafo de cierre:

> Lo que **sí** está garantizado hoy: no se puede introducir un runner paralelo por los scripts del
> proyecto ni por CI, **no se puede romper la jerarquía UI**, no puede existir un test
> silenciosamente muerto, no se filtran secretos, y `QueryBuilder` no construye SQL sin binds.

Es falso, y T20 lo demostró ejecutando: una clase Page-like en `src/screens/` que no extiende
nada, importada directamente por un Step, más `this.pages.<page>.goto(...)` público →
`npm run quality` **exit 0, 62/62**. Los guardrails de UI están anclados por path.

**Después** — la garantía se partió en dos listas explícitas (`CLAUDE.md` §8.1):

- **MACHINE ENFORCED:** runner isolation; **dentro de `src/pages/**`** toda clase extiende
  `BasePage` (A9); **dentro de `src/components/**`** toda clase extiende `BaseComponent` (A10) y no
  usa `this.page` (A11, con el escape F-15); los límites del Step cubiertos por G2/G3/G4/G5; A12;
  secretos; binds de `QueryBuilder`.
- **NOT MACHINE ENFORCED / REVIEW REQUIRED:** clases UI-like fuera de los paths canónicos; patterns
  o directorios UI nuevos que los guardrails no conocen; navegación desde un Step; y todos los
  bypasses F-03 … F-16.

El gap dejó de ser invisible. Ahora tiene ID propio y aparece en cuatro lugares:

| Dónde | Qué dice |
|---|---|
| `CLAUDE.md` §7.5 | el enforcement de UI está **anclado por path**; `quality` verde es necesario y no suficiente |
| `CLAUDE.md` §8, fila **F-17** | el bypass, su reproducción y la consecuencia operativa |
| `CLAUDE.md` §3 | todo objeto UI vive en `src/pages/**` o `src/components/**`; no hay tercera ubicación |
| `README.md` §Architecture Guardrails | fila nueva en la tabla de scope: *"UI classes live in a canonical path — **Nothing, review only**"* |
| `automation-reviewer` checklist #3 y #4 | debe grepear imports no canónicos desde Steps y revisar el path de cada archivo UI del diff |
| `automation-engineer` §MODE: PLAN / IMPLEMENT | paths canónicos no negociables + campo `ARCHITECTURE DEVIATION` |

`F-17` es el ID interno de `H-01`; la equivalencia queda escrita en `CLAUDE.md` §8 para que la
historia no se pierda.

**No se afirma que el bypass fue eliminado.** Sigue siendo técnicamente posible. Lo que cambió es
que ahora está declarado, y que tanto el humano como el Reviewer están instruidos para buscarlo.

## 4. Protected Infrastructure

M-01: `CLAUDE.md` §9 era la lista **menos completa** de las cuatro capas que definen "protegido",
y es justamente la que ambos agentes deben tratar como ley.

`CLAUDE.md` §9 pasó de una lista plana a una tabla con dos capas explícitas:

- **native permission ask** — existe una regla `permissions.ask` en `.claude/settings.json`, así
  que el harness levanta un prompt real. Se agregaron los cuatro paths faltantes:
  `package-lock.json`, `CLAUDE.md`, `.claude/**`, `.mcp.json`.
- **contract-only** — no hay regla nativa; la única barrera es el contrato (`AGENTS.md`,
  `README.md`, los `AGENTS-*.md` de módulo).

Dos precisiones que evitan afirmar una protección que no existe:

1. La regla es `Edit(<path>)` y **no cubre una reescritura por shell** — `automation-engineer`
   tiene `Bash`. Ahí la barrera es contractual, no mecánica (L-11). No se afirma que Bash esté
   técnicamente bloqueado, porque no lo está.
2. Nunca se confirmó empíricamente que el patrón con slash inicial dispare el prompt en runtime
   (L-12, abierto desde T13.1 §10). La lista vale como contrato **aunque** el prompt no aparezca.

`.claude/settings.json` **no fue modificado**. `.mcp.json` se agregó también a la lista de
prohibiciones explícitas del Engineer y al checklist #10 del Reviewer, donde no figuraba en
ninguno de los dos.

Los tres describen el mismo pipeline y las mismas responsabilidades:

```text
/qa-automate → qa-analyst → GATE 1 → automation-engineer MODE: PLAN → GATE 2
             → automation-engineer MODE: IMPLEMENT → automation-reviewer
```

- `qa-analyst` — requerimiento, escenarios, `UNKNOWN`; sin write, sin shell, **sin MCP**.
- `automation-engineer` — único con write; PLAN propone, IMPLEMENT escribe; **MCP sí** (10 tools).
- `automation-reviewer` — review independiente, read-only sobre el repo, reproduce `quality`/E2E
  por su cuenta; **MCP limitado** (5 tools, sin tools de formulario).

Y las reglas del flujo, en los tres documentos: gates humanos, silencio ≠ aprobación,
`CHANGES_REQUESTED` devuelve el control, `VALIDATION_FAILED` detiene, sin auto-approval ni silent
approval, y `quality` verde no sustituye la review.

Numeración: se agregaron secciones **al final** de `CLAUDE.md` (§17) para no invalidar ninguna
referencia existente a §1–§16. En `AGENTS.md` sí hubo renumeración (5→6, 6→7), verificando antes
que ninguna referencia interna o externa apuntara a esas dos secciones.
