## 1. Finding de origen

**F-02 (HIGH)** de `docs/ai-foundation-final-audit.md`: el aislamiento de `oracledb` (el único punto donde este driver crudo, sin tipos, puede tocarse directamente) era bypasseable. El diseño exige que `oracledb` solo se referencie desde `src/database/clients/OracleDatabaseClient.ts`; la auditoría T10 demostró dos formas de evadir tanto ESLint (G4) como el architecture test A6 original:

1. `await import('oracledb')` — un dynamic import, nunca expresado como `import ... from`.
2. `createRequire` con el binding devuelto renombrado — A6 original solo reconocía la variable si se llamaba literalmente `require`.

---

## 2. Riesgo

`oracledb` es un driver sin declaraciones de tipos que el framework aísla deliberadamente detrás de `OracleDatabaseClient` (ver su alias interno `type OraclePool = any`). Si cualquier otro archivo puede tocarlo directamente, se pierde esa frontera: código fuera del cliente autorizado podría abrir pools, ejecutar queries crudas, o depender de detalles internos del driver sin que nada lo señale. El caso del dynamic import es particularmente relevante porque `support/databaseLifecycle.ts` ya usa exactamente ese idioma (`await import(...)`) para cargar `OracleDatabaseClient` de forma perezosa — es el patrón más plausible que alguien (persona o IA) copiaría para cargar `oracledb` directamente.

## 5. Diseño AST

Se amplió A6 (no se creó un invariante nuevo, tal como pedía la tarea) manteniendo `referencesOracledb(sourceFile)` como única función de verificación, reutilizada por los mismos dos `it()` existentes (offender-scan + "el archivo autorizado no quedó obsoleto"). Verificación empírica previa de la forma exacta del AST (script desechable, sin dependencias nuevas, borrado tras confirmar):

```
import('oracledb')                    → CallExpression, expression.kind = ImportKeyword
import { createRequire } from 'module'
  → ImportSpecifier: propertyName=undefined, name='createRequire'
import { createRequire as makeRequire } from 'node:module'
  → ImportSpecifier: propertyName='createRequire', name='makeRequire'
createRequire(...) / makeRequire(...) → CallExpression, expression.kind = Identifier
req('oracledb') / oracleLoader('oracledb') → CallExpression, expression.kind = Identifier
```

Esto confirmó que las tres formas requieren criterios AST distintos y complementarios — ninguna regex podría distinguir de forma confiable un `CallExpression` cuyo callee es la palabra clave `import` de uno cuyo callee es un identificador arbitrario derivado de `createRequire`.

**Limitación deliberada y documentada** (evitando sobreingeniería, tal como autorizaba la tarea): la detección de `createRequire` es de un solo salto — `const X = createRequireLocalName(...); X('oracledb')`. No se cubre reasignación posterior de `X`, desestructuración, propiedades de objeto/clase (`this.req = createRequire(...)`), ni pasar el loader como parámetro entre funciones. Cubrir esos casos exigiría un analizador de flujo de datos completo del programa — exactamente lo que la tarea pedía documentar como límite en vez de construir. Ninguna de esas formas fue demostrada como alcanzable por la auditoría T10; las que sí lo fueron (createRequire importado normal, aliasado, asignado a variable, variable usada para cargar el módulo) están cubiertas.

## 8. createRequire aliases

Dos funciones nuevas que preceden el escaneo principal:

```ts
function findCreateRequireLocalNames(sourceFile): Set<string> {
  // recorre ImportDeclaration con moduleSpecifier 'module' | 'node:module';
  // para cada ImportSpecifier cuyo nombre importado (propertyName ?? name)
  // sea 'createRequire', registra el nombre LOCAL (name.text) —
  // el alias si lo hay, el nombre original si no.
}

function findRequireLikeLocalNames(sourceFile, createRequireLocalNames): Set<string> {
  // recorre VariableDeclaration con inicializador CallExpression cuyo
  // callee es un Identifier presente en createRequireLocalNames;
  // registra el nombre de la variable declarada, sin importar cómo se llame.
}
```

Y el tercer caso dentro de `referencesOracledb`:

```ts
if (ts.isIdentifier(node.expression) && requireLikeLocalNames.has(node.expression.text)) {
  found = true;
  return;
}
```

**Resultado:**
- `import { createRequire } from 'node:module'; const req = createRequire(...); req('oracledb')` → **detectado**.
- `import { createRequire as makeRequire } from 'node:module'; const oracleLoader = makeRequire(...); oracleLoader('oracledb')` → **detectado**, con el import Y la variable aliasadas simultáneamente.
- El patrón real de `OracleDatabaseClient.ts` (`import { createRequire } from 'module'; const require = createRequire(...); const oracledb = require('oracledb');`, especifier `'module'`, no `'node:module'`) sigue reconociéndose — el nombre local `require` se descubre igual que cualquier otro, ya no por comparación literal sino porque proviene de `createRequire`.

## 15. Aprendizaje técnico

1. **Rastrear un binding por su origen estructural, no por su nombre literal, es lo que hace que un guardrail sobreviva a un rename.** El A6 original comparaba `node.expression.text === 'require'` — una comparación de texto que cualquier `rename` de variable rompe trivialmente. La versión nueva pregunta "¿de dónde vino esta función?" (¿fue devuelta por `createRequire`, sin importar cómo se llame la variable?), que es exactamente la pregunta que importa y la única que no se rompe con un alias.

2. **Dos pasadas sobre el AST, en vez de una, evitan depender del orden en que aparece el código.** `findCreateRequireLocalNames` y `findRequireLikeLocalNames` se ejecutan completas ANTES de escanear los usos — así, un archivo donde el import de `createRequire` aparece después de su uso (sintácticamente inválido en la práctica, pero conceptualmente posible en otros órdenes de declaración) igual se resolvería correctamente. Intentar hacerlo en una sola pasada habría exigido resolver todo en el orden exacto en que el parser visita los nodos, una fragilidad innecesaria cuando dos pasadas simples lo evitan por completo.

3. **Verificar la forma exacta del AST antes de escribir cada uno de los tres casos evitó adivinar tres veces en lugar de una.** El dynamic import (`ImportKeyword`) y el `createRequire` aliasado (`ImportSpecifier.propertyName` vs `.name`) tienen representaciones de AST completamente distintas entre sí y respecto al import estático ya existente — confirmarlas con un script desechable antes de tocar el archivo real evitó que cualquiera de los tres casos se basara en una suposición incorrecta sobre cómo el compilador realmente representa cada forma.

4. **Ampliar un test existente en vez de crear uno nuevo es la decisión correcta cuando el invariante conceptual no cambió, solo su cobertura.** F-02 no introdujo una regla nueva ("`oracledb` solo se referencia desde el cliente autorizado" ya existía desde T05/T06) — solo demostró que la implementación de esa regla tenía huecos. Ampliar `referencesOracledb` mantuvo el conteo total de tests en 61 y el propio invariante A6 como el único lugar del código que necesita entender "qué cuenta como referenciar oracledb", en vez de duplicar esa noción en un A13 separado que tendría que mantenerse sincronizado con A6.

5. **Documentar una limitación deliberada en el propio comentario del código (no solo en un registro histórico) mantiene la limitación visible para quien lea el test, no solo para quien lea la trazabilidad.** El comentario agregado a A6 dice explícitamente qué formas NO cubre (reasignación, desestructuración, propiedades de objeto) y por qué (evitar un analizador de flujo de datos completo para una tarea que no lo pedía) — así, un futuro lector del propio `architecture.test.ts` entiende el límite sin tener que encontrar y leer `T10.3-oracledb-isolation.md` primero.

6. **Aislar la causa de un fallo compuesto (fixture 4 cubierto por ESLint, fixtures 1-3 cubiertos solo por A6) mejora la calidad de la evidencia, no solo su presentación.** La primera corrida de `npm run quality` con los 4 fixtures falló en `lint`, antes de llegar a `test:unit` — técnicamente demostraba "quality falla", pero no demostraba específicamente que A6 detecta los 3 bypasses nuevos, porque el chequeo nunca llegó a ejecutarse. Repetir la prueba sin el fixture ya cubierto por ESLint fue necesario para que la evidencia respaldara la afirmación real: es A6, y no otra cosa, lo que ahora cierra F-02.
