## 1. Finding de origen

**F-01 (HIGH)** de `docs/ai-foundation-final-audit.md`, en su aspecto restante tras `T10.1-ui-hierarchy-guardrail.md`. T10.1 cerró que un Component pueda extender `BasePage` en lugar de `BaseComponent` (A9/A10). Pero la propia auditoría T10 (fixture L2, `AuditUnscopedComponent`) demostró un segundo bypass, independiente del primero: un Component que **sí** extiende `BaseComponent` correctamente puede, aun así, ignorar su `root` y construir locators directamente desde `this.page` — con `npm run quality` en verde. T10.1 documentó este aspecto en su §11 como una propuesta evaluada pero deliberadamente no implementada, reservándolo para una tarea separada. Esta es esa tarea.

---

## 2. Riesgo

Un Component que construye locators desde `this.page` en lugar de `this.root` deja de estar realmente scoped a la región que dice representar (p. ej. la barra de navegación) — cualquier método podría, por accidente o por copiar mal el patrón, construir un locator sobre el documento completo. Es exactamente la garantía que `root: Locator` existe para dar (ver README, sección Components: "Every locator inside the Component is built from `this.root` — never `this.page` directly"), y antes de esta tarea era una afirmación de documentación sin ningún mecanismo que la hiciera cierta.

---

## 3. Invariante

Toda clase concreta bajo `src/components/**` (excluyendo `src/components/base/BaseComponent.ts`) no debe referenciar `this.page` en ninguno de sus miembros — constructor incluido. El único uso legítimo de `page` dentro de un Component es el **parámetro local** del constructor (un `Identifier` plano, nunca una propiedad heredada), usado para construir `root` antes de llamar a `super(page, root)` — exactamente el patrón de `ExampleNavigationComponent`.

### 4.2. Verificación previa de la forma exacta del AST

Antes de escribir la regla, se confirmó empíricamente (script temporal, `typescript` ya instalado, sin dependencias nuevas, borrado inmediatamente después de usarlo) la forma exacta que produce el compilador para `this.page`:

```
this.page.getByRole(...) → PropertyAccessExpression "this.page.getByRole", expression.kind=PropertyAccessExpression
                            └── PropertyAccessExpression "this.page",            expression.kind=ThisKeyword, name="page"
const x = this.page       → PropertyAccessExpression "this.page",                expression.kind=ThisKeyword, name="page"
page.getByRole(...)       → PropertyAccessExpression "page.getByRole",           expression.kind=Identifier,  name="getByRole"
```

Esto confirmó el diseño preferido por la tarea: una **única** comprobación —`PropertyAccessExpression` cuyo `expression.kind === ts.SyntaxKind.ThisKeyword` y cuyo `name.text === 'page'`— detecta tanto `this.page` usado solo como encadenado (`this.page.getByRole(...)`, `this.page.locator(...)`, etc.), porque el nodo interno `this.page` siempre existe como parte de la cadena. No hace falta una lista de métodos prohibidos (`getByRole`, `getByText`, `locator`, `getByLabel`, ...) — bloquear el receptor `this.page` en sí basta y es más simple y más seguro, tal como pedía la tarea. El parámetro local `page.getByRole(...)` produce una forma de AST completamente distinta (`expression.kind === Identifier`) y nunca coincide.

### 4.3. Implementación

Nuevo bloque en `src/architecture.test.ts`, a continuación de A10 (T10.1):

```ts
function getThisPageAccessLines(sourceFile: ts.SourceFile, classNode: ts.ClassDeclaration): number[] {
  const lines: number[] = [];

  function visit(node: ts.Node): void {
    if (
      ts.isPropertyAccessExpression(node) &&
      node.expression.kind === ts.SyntaxKind.ThisKeyword &&
      node.name.text === 'page'
    ) {
      const { line } = sourceFile.getLineAndCharacterOfPosition(node.getStart(sourceFile));
      lines.push(line + 1);
    }
    ts.forEachChild(node, visit);
  }

  for (const member of classNode.members) visit(member);
  return lines;
}

describe('architecture — Components scope UI access through root, not this.page', () => {
  it('never accesses this.page directly (locators must be built from this.root)', () => {
    const files = walkRepoFiles().filter(
      (relativePath) =>
        relativePath.startsWith('src/components/') &&
        relativePath.endsWith('.ts') &&
        !relativePath.endsWith('.test.ts') &&
        relativePath !== COMPONENTS_BASE_FILE
    );

    const offenders: string[] = [];

    for (const relativePath of files) {
      const sourceFile = readSourceFile(relativePath);

      function visitClasses(node: ts.Node): void {
        if (ts.isClassDeclaration(node) && node.name) {
          const className = node.name.text;
          for (const line of getThisPageAccessLines(sourceFile, node)) {
            offenders.push(`${relativePath}:${line} (class ${className})`);
          }
        }
        ts.forEachChild(node, visitClasses);
      }

      visitClasses(sourceFile);
    }

    assert.deepEqual(
      offenders,
      [],
      `Components must scope UI access through this.root, never this.page. Offenders: ${offenders.join('; ') || '(none)'}`
    );
  });
});
```

Numerado **A11** (continuando A9/A10 de T10.1, sin reutilizar A8 — reservado conceptualmente desde T06 para el guardrail de `process.env`, ver `T10.1-ui-hierarchy-guardrail.md` §5).

Reutiliza `walkRepoFiles`, `readSourceFile` y la constante `COMPONENTS_BASE_FILE` ya definidas por T06/T10.1 — ninguna infraestructura nueva. Cero dependencias nuevas (`typescript` ya es una dependencia del archivo desde T06).

**Por qué recorre el constructor también, sin tratarlo como caso especial:** el enunciado "no bloquear el parámetro local `page` del constructor" no requiere excluir el constructor de la búsqueda — el propio AST ya distingue ambos casos por construcción: el parámetro local es un `Identifier`, nunca una `PropertyAccessExpression` sobre `this`. No hacía falta (ni se agregó) ninguna lógica de "si es el constructor, saltear" — habría sido una excepción redundante sobre algo que el AST ya resuelve solo.

## 11. Aprendizaje técnico

1. **Cuando el AST distingue naturalmente dos casos, no hace falta escribir lógica para distinguirlos.** La instrucción "no bloquees el parámetro local `page` del constructor" sonaba como si necesitara una excepción explícita (`if (isInsideConstructor) skip`). No la necesitó: un parámetro de función es un `Identifier` y una propiedad heredada accedida como `this.page` es una `PropertyAccessExpression` sobre un `ThisExpression` — son nodos de tipo distinto desde el parser. Buscar la forma AST correcta antes de escribir la regla evitó una condición extra que habría sido, en el mejor caso, redundante, y en el peor, una fuente de falsos negativos si alguna vez se escribía mal.

2. **Una comprobación sobre el receptor (`this.page`) generaliza mejor que una lista de métodos prohibidos (`getByRole`, `getByText`, `locator`, ...).** La tarea explícitamente prefería esta forma ("sería más simple y más seguro que mantener una lista de métodos"), y la verificación empírica del AST lo confirmó: `this.page.getByRole(...)` y `this.page.locator(...)` comparten el mismo nodo interno `this.page` como parte de la cadena de `PropertyAccessExpression`, así que una sola regla los cubre a ambos — y a cualquier método futuro de `Page` que aún no exista, sin tener que actualizar una lista cada vez que Playwright agregue un nuevo `getBy*`.

3. **Verificar la forma exacta del AST con un script desechable, antes de escribir la regla "en serio", evita apostar la implementación a una suposición.** Se podría haber asumido "seguro que `this.page` es un solo nodo" y escrito la regla directamente — en cambio, un script de 15 líneas confirmó en segundos que el nodo `this.page` existe como paso intermedio dentro de `this.page.getByRole(...)`, lo cual es la premisa entera del diseño de "una sola comprobación cubre todo". Confirmar antes de construir es más barato que descubrir después, con un fixture que no falla como se esperaba, que la suposición estaba equivocada.

4. **Dos aspectos de un mismo finding (F-01) pudieron cerrarse en dos tareas independientes, cada una con su propio test, sin que una dependiera de que la otra ya hubiera corrido.** A11 no verifica "¿esta clase extiende `BaseComponent`?" (eso es A10) — verifica "¿esta clase usa `this.page`?", sin importar qué extienda. Esto significa que A10 y A11 son ortogonales: un Component que falle A10 (extiende `BasePage`) puede además fallar A11 si también usa `this.page`, y ambos fallos aparecerían de forma independiente y con su propio mensaje — ninguno oculta al otro.

5. **Reconfirmar las premisas contra el código real antes de escribir una sola línea del test es lo que hace que la implementación no dependa de lo que dice un documento histórico.** Las 5 afirmaciones que la tarea pedía reconfirmar (§4.1) no eran retóricas: si `BaseUiObject` hubiera tenido, por ejemplo, un método que sí necesitara `this.page` para algo legítimo, A11 tal como está diseñado habría producido falsos positivos en cada Component. Verificarlo con `grep` antes de codificar convirtió una suposición razonable en un hecho confirmado.
